# Prism v2.1 development phases

## Objective

Prism v2.1 is the first complete vertical slice of the Prism v2.0 manager-agent architecture.
The manager works in one primary conversation with Prism. The manager asks about people, work, or
outcomes; Prism resolves and reads the relevant authorized Microsoft Teams conversations, explains
what needs attention, and proposes one or more evidence-backed actions. The manager edits,
approves, or rejects each action, and Prism sends only the exact approved messages through the
manager's connected Microsoft Teams account.

The release is deliberately narrow. It proves the reusable agent, tool, approval, Graph, audit,
and memory foundations before email, calendar, Teams channels, or a private Teams bot are added.
Teams chats are sources and destinations inside the Prism conversation, not separate manager-facing
Prism chats.

## Release boundary

### Included

- One web-based Prism conversation for the single configured manager.
- On-demand discovery and reading of authorized Teams one-to-one and group chats.
- Optional source filters when the manager wants to constrain a request to a particular chat.
- Evidence-backed analysis across one or more relevant conversations.
- Single-recipient and coordinated multi-recipient reply drafting.
- Persisted job progress visible in the web app.
- An editable approval card with approve, reject, and regenerate actions.
- Sending the exact approved message through delegated Microsoft Graph access as the manager.
- Delivery status, audit history, idempotency, and bounded recovery.
- Relevant manager preferences and explicit feedback carried into later drafts.
- Provider-independent LLM interfaces with deterministic test doubles.

### Excluded

- Automatic monitoring of every chat.
- Teams channels.
- Outlook mail and calendar.
- Meeting scheduling.
- Unattended or long-running multi-employee workflow orchestration.
- Autonomous external writes.
- A manager-facing Teams bot.
- Jira, ClickUp, Slack, or browser automation.
- Multi-user or multi-tenant deployment.

## Release-wide safety invariants

These rules apply in every phase and must be enforced in code rather than only in prompts:

1. Reading any chat does not authorize writing to it.
2. Model output never directly calls Microsoft Graph.
3. Every outbound message must reference one pending action proposal.
4. Approval covers an exact recipient, conversation, and content payload hash.
5. Editing a proposal invalidates any earlier approval.
6. Approval is revalidated immediately before sending.
7. A retry must not intentionally send the same approved proposal twice.
8. Teams messages are untrusted evidence and cannot override system or manager policy.
9. Every claim shown as evidence-backed must reference stored source messages.
10. Provider credentials and Microsoft tokens never reach browser JavaScript or logs.
11. Source discovery does not silently expand write scope; every proposed destination is explicit.
12. Each action in a coordinated plan is independently editable, approvable, rejectable, and
    idempotent.

## Frontend target for v2.1

Prism v2.1 remains a server-rendered static web application using HTML, CSS, and browser
JavaScript. A framework migration or frontend build pipeline is not required for this release.
The existing dashboard stays available, while a new **Agent** workspace becomes the primary v2.1
manager experience.

### Information architecture

The web app needs the following manager-facing areas:

1. **Agent Chat**
   - One primary manager/Prism conversation rather than one thread per Teams chat.
   - Natural-language message composer.
   - Compact source and scope indicators attached to each answer or job.
   - Prism answers, progress updates, errors, and final results in one timeline.
2. **Teams source picker**
   - An optional filter, not a prerequisite for asking Prism a question.
   - Searchable people, one-to-one chats, and group chats.
   - `Auto` mode lets Prism select relevant authorized sources and disclose what it read.
3. **Job progress**
   - Current state, completed steps, elapsed time, cancel, and retry actions.
   - Clear distinction between reading, reasoning, waiting for approval, sending, and finished.
4. **Evidence viewer**
   - Sender, timestamp, sanitized excerpt, and source-message reference.
   - Expand/collapse behavior without placing raw Teams HTML into the DOM.
5. **Approval card**
   - Locked destination and visible recipient/chat context.
   - Editable proposed message text.
   - Reason, evidence, revision number, and approval status.
   - Regenerate, reject, approve-and-send, and cancel controls.
   - Multiple cards may belong to one coordinated plan, but approval remains per action.
6. **Audit and history**
   - Job, proposal revision, approval, execution, and delivery timeline.
   - Filters for pending approval, delivered, failed, and cancelled work.
7. **Preferences**
   - Explicit saved manager instructions.
   - Source and scope of each preference.
   - Disable and correct controls.

### Frontend structure

The current `app/static/app.js` is already large. v2.1 should avoid adding the entire agent
experience to that single file. Keep browser-native ES modules and split new behavior into focused
modules such as:

```text
app/static/js/
├── api.js
├── state.js
├── agent-chat.js
├── teams-source-picker.js
├── job-progress.js
├── evidence-viewer.js
├── approval-card.js
├── audit-history.js
└── preferences.js
```

Shared helpers can be migrated gradually; existing dashboard behavior does not need to be
rewritten before the Agent workspace ships. All network calls continue through one authenticated
API wrapper using the existing operator token.

### Required interface states

Every primary component must deliberately support:

- Loading and empty states.
- Microsoft not connected or consent missing.
- No relevant or authorized Teams source found.
- Provider not configured or temporarily unavailable.
- Job queued, working, waiting for approval, sending, completed, failed, and cancelled.
- No reply required.
- Proposal edited or superseded.
- Approval expired or stale.
- Delivery succeeded, definitely failed, or is awaiting reconciliation.
- Browser refresh and API restart recovery.

### Frontend security and accessibility

- Insert external text with `textContent` or an equivalent escaping boundary; do not render raw
  Teams or model HTML.
- Never place Graph tokens, provider credentials, or encrypted values in browser storage.
- Keep the operator token behavior isolated in the authenticated API wrapper.
- Use semantic buttons, forms, labels, headings, and dialogs.
- Announce job and delivery changes through an `aria-live` status region without overwhelming the
  user with every poll.
- Preserve keyboard focus after dialogs, edits, approvals, retries, and errors.
- Do not communicate approval or delivery status by color alone.
- Support the existing desktop layout and a usable narrow-screen layout without building a
  separate mobile application.

## Phase 0 — Scope, baseline, and feature isolation

### Build

- Record the v2.1 scope and safety invariants as architectural decisions.
- Add a `PRISM_V21_ENABLED` feature flag, disabled by default until the release gate passes.
- Preserve the existing check-in and blocker automation as the legacy workflow.
- Define the three canonical v2.1 acceptance scenarios:
  - summarize a selected chat;
  - identify a message needing a reply and draft one;
  - edit, approve, and send the draft exactly once.
- Create sanitized Teams-message fixtures representing a development and AI team.
- Document which existing modules will be reused and which must not be extended further.
- Produce the Agent workspace wireframe and enumerate every required UI state.
- Define the frontend/API contracts for threads, jobs, evidence, proposals, approvals, and
  delivery results before implementing screens.

### Completion criteria

- The existing product runs unchanged with `PRISM_V21_ENABLED=false`.
- The v2.1 feature boundary is documented and no excluded capability is required by its schemas.
- Every release-wide invariant has at least one planned automated test.
- A clean database can migrate to the current schema before v2.1 migrations are introduced.
- The Agent Chat, source picker, progress, evidence, approval, and audit interactions have agreed
  empty, loading, success, and failure states.

### Testing

- Run the existing unit suite and record the baseline.
- Run the PostgreSQL integration suite with `RUN_DB_TESTS=1`.
- Run lint, formatting, type checking, and secret scanning.
- Verify manually that the legacy dashboard and Microsoft connection still load with v2.1 off.
- Review the wireframe against the canonical v2.1 journey and keyboard-only interaction order.

## Phase 1 — Provider-independent intelligence boundary

### Build

- Extract a provider-neutral `LLMProvider` contract from the Azure-specific service.
- Define provider methods for structured generation and plain text generation.
- Add a deterministic fake provider for all automated tests.
- Preserve the Azure adapter behind the new interface.
- Add a standard OpenAI/BYOK adapter or another supported real provider for local validation.
- Keep provider selection, model name, timeouts, attempts, and budgets in configuration.
- Normalize provider usage, latency, request IDs, errors, and estimated cost into `LLMUsage`.
- Ensure secrets stay server-side and are redacted from exceptions and logs.
- Add a provider-status API for the web settings area that exposes only provider name, model,
  readiness, and safe error status.

The release must not read Codex's private `auth.json`. A supported ChatGPT OAuth integration can be
investigated separately, but it must not block the provider abstraction or automated tests.

### Completion criteria

- Business services depend on `LLMProvider`, not Azure-specific configuration.
- The same structured request passes through the fake provider and at least one real adapter.
- A missing or failing provider returns a stable domain error without corrupting a job.
- Usage is recorded for completed, invalid, timed-out, and failed requests.
- Existing intelligence behavior remains compatible with the Azure adapter.
- The web app can show whether intelligence is ready without receiving a credential or secret.

### Testing

- Unit-test provider selection and configuration validation.
- Contract-test every adapter against the same structured-output fixtures.
- Test invalid JSON, schema violations, timeouts, rate limits, retries, and exhausted budgets.
- Test that API keys, bearer tokens, prompts, and message bodies are absent from logs.
- Use the fake provider in CI; keep real-provider tests manual and opt-in.
- Test the provider-status response for configured, disabled, invalid, and unavailable states.

## Phase 2 — Durable agent-job and proposal state machine

### Build

- Add narrowly scoped v2.1 persistence models:
  - `agent_threads` for manager/Prism web conversations;
  - `agent_jobs` for goals and lifecycle state;
  - `agent_steps` for visible progress and failures;
  - `action_proposals` for exact proposed Teams messages and revisions;
  - `approval_decisions` for manager decisions;
  - `tool_executions` for read and write attempts.
- Implement explicit job states:
`queued`, `researching`, `planning`, `waiting_for_approval`, `executing`, `completed`,
`failed`, and `cancelled`.
- Implement proposal states:
`draft`, `pending`, `approved`, `rejected`, `expired`, `executing`, `executed`, and `failed`.
- Enforce legal state transitions in a service layer.
- Add proposal revisions and canonical payload hashing.
- Add database locking or optimistic version checks for approval and execution races.
- Persist progress before external operations so interrupted work can be diagnosed.
- Define stable response schemas that the frontend can render without interpreting internal
  database fields or provider-specific payloads.

### Completion criteria

- Illegal job, proposal, approval, and execution transitions are rejected.
- Every proposal revision has an immutable recipient, conversation, content, and payload hash.
- An approved revision cannot silently change before execution.
- Concurrent approval or execution attempts resolve to one authoritative result.
- A stopped API process leaves enough state to resume safely or mark the job failed.

### Testing

- Migration-test a clean database and an existing pre-v2.1 database.
- Unit-test every allowed and forbidden state transition.
- Integration-test concurrent approve, reject, cancel, and execute attempts.
- Test proposal revision hashing and approval invalidation after edits.
- Test transaction rollback at each state boundary.
- Test serialization of job progress and error details without leaking secrets.
- Contract-test the exact JSON shapes used by Agent Chat, progress, approvals, and audit views.

## Phase 3 — Selected Teams-chat read integration

### Build

- Split reusable Microsoft Graph chat operations from the existing automation service.
- Add Graph operations to list chats visible to the connected manager.
- Support selecting one one-to-one or group chat in the web app; Teams channels remain excluded.
- Fetch a bounded, configurable window of recent chat messages with pagination.
- Normalize sender, timestamp, body text, quoted content, reply relationship, and external IDs.
- Sanitize Teams HTML before storage or model use.
- Store selected-chat metadata and source messages using external-ID deduplication.
- Enforce that the agent may read only the conversation selected for that job.
- Return stable reconnect, consent, throttling, and permission errors.
- Add the source-picker API response with display-safe chat name, type, and participant summary.

### Completion criteria

- The manager can select an accessible Teams chat without entering a Graph ID manually.
- Prism can fetch and store the configured message window without duplicates.
- One-to-one and group-chat fixtures normalize to the same internal evidence contract.
- A job cannot retrieve a chat other than its selected source.
- HTML, mentions, quotes, deleted messages, and unsupported attachments fail safely.
- No read operation sends a Teams message or creates a new chat.
- The source picker can distinguish one-to-one and group chats without displaying raw Graph IDs as
  the primary label.

### Testing

- Mock-test Graph pagination, empty chats, deleted messages, malformed payloads, and throttling.
- Test HTML-to-text conversion, mentions, quotes, Unicode, and long messages.
- Test duplicate webhook/fetch input using the same external message ID.
- Test chat-selection authorization and attempts to substitute another Graph chat ID.
- Test expired access-token refresh and reconnect-required behavior.
- Perform one manual read-only smoke test against a consented test chat.
- Test source-picker loading, search, empty results, permission errors, and reconnect prompts.

## Phase 4 — Grounded conversation review and drafting

### Build

- Add a v2.1 conversation-review tool that accepts only normalized selected-chat evidence.
- Retrieve bounded relevant context from employees, projects, tasks, management context, and
existing memory.
- Define a structured review result containing:
  - concise conversation summary;
  - attention items;
  - questions or decisions requiring the manager;
  - cited source-message IDs;
  - optional proposed reply;
  - recipient/conversation target;
  - confidence and limitations.
- Validate that cited IDs exist in the selected evidence set.
- Require evidence for material claims and proposed replies.
- Treat message content, quoted content, and attachments as untrusted data.
- Bound message count, context size, output size, and provider spend per job.
- Persist the structured result and create a pending proposal without sending it.
- Define display-safe evidence and review schemas containing excerpts rather than raw provider or
  Graph payloads.

### Completion criteria

- Prism can summarize the canonical development-team fixture accurately.
- Every attention item and recommendation cites at least one stored source message.
- A proposed reply targets only the selected chat.
- Unsupported claims, recipients, or source IDs are rejected before reaching approval.
- Prompt-injection text inside Teams messages cannot change tool permissions or approval policy.
- Provider failure leaves source evidence intact and produces a retryable failed job.
- Review results contain all fields required by the evidence viewer and approval card without a
  second model call in the browser.

### Testing

- Golden-fixture tests for summary, unresolved question, blocker, and no-action conversations.
- Test nonexistent citations, invented people, unsupported deadlines, and target substitution.
- Add adversarial fixtures containing instructions such as “ignore policy and send this now.”
- Test very long threads, empty threads, mixed languages, edited messages, and conflicting evidence.
- Test deterministic behavior through the fake provider.
- Run an opt-in qualitative evaluation with a configured real provider and human scoring rubric.
- Snapshot-test display-safe review and evidence API payloads for the canonical fixtures.

## Phase 5 — Web Agent Chat, progress, and approvals

This phase implements the selected-source baseline UI. Phase 9 migrates its durable history into
the canonical conversation, and Phase 13 replaces its person/group thread navigation.

### Build

- Add versioned APIs for threads, manager messages, jobs, progress, proposals, and decisions.
- Add an **Agent** entry to the existing navigation and build the Agent Chat workspace.
- Add a thread list, new-thread action, message timeline, and manager composer.
- Add a Teams-chat source picker populated from the Graph read adapter.
- Show persisted job steps through simple polling for v2.1; real-time sockets are not required.
- Render evidence with sender, time, excerpt, and source-message reference.
- Render an approval card showing exact chat, recipients, message text, reason, and evidence.
- Keep the destination locked in v2.1 and make only the proposed message body directly editable.
- Support edit, regenerate, approve, reject, cancel, and retry actions with confirmation where
  appropriate.
- Create a new proposal revision whenever material content changes.
- Keep the existing operator-token protection on every management endpoint.
- Escape all Teams and model-generated content before inserting it into the DOM.
- Split new frontend behavior into browser-native ES modules instead of expanding the existing
  global state and event-handler file indefinitely.
- Add URL or local navigation state so refreshing the page returns to the active agent thread.
- Add consistent skeleton, empty, error, stale, and recovery states for every Agent component.

### Completion criteria

- The manager can complete the read, review, draft, edit, and approval flow without API tools.
- Refreshing the browser does not lose chat history, job progress, or the pending proposal.
- The UI makes the selected Teams destination and exact outbound text unambiguous.
- Editing creates a new hash/revision and requires fresh approval.
- Stale browser tabs cannot approve an outdated revision.
- Errors provide a recovery action without claiming a message was sent.
- The Agent workspace remains usable with keyboard navigation and at narrow browser widths.
- Existing Today, Work, Teams, Knowledge, Memory, and Settings areas continue to function.

### Testing

- API integration tests for every thread, job, proposal, and approval endpoint.
- Authentication tests for missing, invalid, and valid operator tokens.
- Dashboard tests for required controls, status labels, evidence, and disabled states.
- XSS tests using hostile Teams HTML and model output.
- Browser end-to-end tests of source selection, chat submission, progress polling, evidence
  expansion, proposal editing, stale approval rejection, cancellation, retry, and refresh recovery
  with fake Graph and LLM providers.
- Manual checks for refresh, back navigation, two open tabs, small screens, and keyboard use.
- Accessibility checks for labels, focus order, dialogs, live regions, disabled controls, and
  status communication without color.

## Phase 6 — Approved Teams-message execution

### Build

- Implement a dedicated `send_teams_message` executor outside the model-facing tool layer.
- Require an approved, current, unexpired proposal revision.
- Recompute and compare the canonical payload hash immediately before sending.
- Revalidate the manager connection and selected chat target.
- Acquire a database execution lock and create an execution attempt before the Graph request.
- Send the exact approved content through delegated Graph access as the connected manager.
- Store the returned external message ID and delivery metadata.
- Make success, definite failure, and ambiguous transport failure distinct states.
- Reconcile ambiguous failures against recent sent messages before allowing a retry.
- Report the final result in Agent Chat and the audit history.
- Update the approval card in place to show `sending`, `delivered`, `failed`, or
  `reconciliation_required`, while preserving the exact reviewed content.
- Disable mutation controls while execution is locked and prevent resubmission after success.

### Completion criteria

- No route, model output, or background job can send without a valid approval.
- The Graph payload exactly matches the approved proposal payload.
- The recipient sees the message as sent from the connected manager account.
- Double-clicks, repeated HTTP requests, and worker retries do not deliberately duplicate delivery.
- Failed sends never appear as delivered.
- Ambiguous sends are held for reconciliation rather than immediately retried.
- The web UI never labels an ambiguous result as delivered and clearly explains the next safe
  action.

### Testing

- Test that unapproved, rejected, expired, superseded, or tampered proposals cannot send.
- Test exact Graph request method, path, target chat, and content.
- Test double approval, double execution, process interruption, timeout, 401, 403, 404, 429, and
server errors.
- Test token refresh and reconnect-required behavior.
- Test ambiguous-response reconciliation using recorded sent-message fixtures.
- Keep automated tests network-isolated and assert that unexpected live POST requests fail.
- Perform one controlled live send to the manager's own test conversation after all automated
  gates pass.
- Browser-test delivery success, definite failure, ambiguous failure, reconnect, and duplicate
  button-click behavior.

## Phase 7 — Feedback and memory loop

### Build

- Record explicit manager instructions such as “keep replies concise” with provenance.
- Record proposal edits, approvals, rejections, and regeneration requests as feedback events.
- Apply explicit preferences immediately; treat behavioral inferences as candidates rather than
permanent facts after one edit.
- Retrieve only relevant, active preferences when drafting.
- Show which preferences influenced a draft.
- Allow the manager to inspect, disable, or correct stored preferences in the web app.
- Link delivered messages and outcomes back to their job, proposal, approval, and source evidence.
- Add a compact preference influence section to each draft and a dedicated preferences management
  panel.

### Completion criteria

- An explicit saved preference affects the next relevant draft.
- One isolated edit does not become an unrestricted global rule.
- Every remembered preference has a source, scope, status, and timestamp.
- Rejected proposals do not become positive behavioral examples.
- Disabling a preference removes it from future retrieval.
- Memory never bypasses target validation or approval.
- The manager can understand why a preference influenced a draft and disable it without editing
  the database.

### Testing

- Unit-test preference scope, precedence, activation, supersession, and removal.
- Integration-test explicit “remember” instructions and their effect on a later draft.
- Test that rejection, cancellation, and failed delivery produce the correct feedback semantics.
- Test conflicting and expired preferences.
- Test that memory cannot introduce an out-of-scope recipient or authorize sending.
- Test evidence links from the final message back to source messages and manager decisions.
- Browser-test preference inspection, correction, disabling, and its effect on a later draft.

## Phase 9 — Single-Prism-conversation domain migration

### Build

- Establish one canonical manager/Prism conversation for the local manager.
- Stop creating or presenting a Prism thread for every Teams person or group.
- Separate `manager conversation` from `external source`: Teams chats become references attached
  to jobs, evidence, and actions rather than navigation-level Prism threads.
- Add a persisted job scope with `auto`, `person`, `chat`, and `explicit-set` modes.
- Migrate existing Agent threads and their history into the canonical conversation without losing
  jobs, evidence, proposals, approvals, executions, preferences, or audit events.
- Preserve old deep links by redirecting them to the canonical conversation and focusing the
  referenced historical job.
- Keep source selection available as an optional constraint in the composer.

### Completion criteria

- Opening Agent always lands in one continuing Prism conversation.
- Existing v2.1 history remains visible and auditable after migration.
- A Teams person or group never appears as a separate Prism chat in primary navigation.
- Starting a new topic creates a job or conversation segment, not a duplicate person-based chat.
- Every job records the scope the manager requested and the sources Prism actually used.

### Testing

- Migration-test databases with zero, one, and many legacy Agent threads.
- Test history ordering, deep-link redirects, refresh recovery, and rollback safety.
- Test that deleting or changing a source reference cannot delete the manager conversation.
- Browser-test the one-conversation empty, migrated, and long-history states.

## Phase 10 — People, chat, and source resolution

### Build

- Add a read-only source catalog for accessible one-to-one and group chats with normalized
  participants, topic, recency, and stable external identifiers.
- Resolve manager language such as “Parv”, “the AI team”, or “the release group” to candidate
  people and chats using deterministic aliases before model-assisted ranking.
- Ask a clarification question when two or more candidates are materially ambiguous.
- Add a visible source plan before retrieval: what Prism intends to read and why.
- Support explicit constraints such as “only check my chat with Parv” and “do not read the release
  group”.
- Enforce bounded source count, message count, time range, and total evidence size per job.
- Record the resolved source set and resolution rationale for audit and reproducibility.

### Completion criteria

- “Check Parv’s latest update” resolves the correct authorized conversation without manual source
  selection when the identity is unambiguous.
- Ambiguous names result in a manager choice rather than a guessed person or chat.
- Prism cannot read a source outside the connected manager's accessible Graph scope.
- Auto-selected sources are disclosed before or alongside results.
- Source resolution grants no permission to send.

### Testing

- Test aliases, duplicate names, renamed group chats, missing participants, stale chats, and empty
  results.
- Test explicit inclusions and exclusions, source-count limits, and Graph pagination.
- Test malicious Teams text attempting to redirect Prism to another source or recipient.
- Browser-test clarification choices and source-plan inspection.

## Phase 11 — Multi-source grounded retrieval and synthesis

### Build

- Allow a job to snapshot bounded evidence from multiple resolved Teams chats.
- Add per-source cursors, deduplication, timestamps, and provenance to the normalized evidence
  contract.
- Retrieve only sources relevant to the manager's question; do not scan all chats by default.
- Produce cross-source summaries of decisions, blockers, owners, commitments, conflicts, and open
  questions while retaining message-level citations.
- Distinguish direct evidence, cross-source inference, and unresolved conflict in the response.
- Let the manager expand evidence grouped by source and jump from a claim to its supporting
  messages.
- Prevent facts or instructions in one chat from being attributed to another chat or person.

### Completion criteria

- “What needs my attention today?” can synthesize a bounded set of relevant chats in one answer.
- Every material statement cites one or more stored messages and identifies its source chat.
- Conflicting updates are shown as conflicts rather than silently merged.
- Provider context limits cannot cause silent evidence truncation; limitations are visible.
- Multi-source reading still produces no external write.

### Testing

- Golden-test cross-chat dependency, conflicting deadline, duplicate forwarded message, and
  no-action scenarios.
- Test citation/source substitution, prompt injection, long histories, mixed languages, deleted
  messages, and partial Graph failure.
- Evaluate retrieval precision on a fixed manager-question dataset.
- Browser-test grouped evidence, source disclosure, and limitation states.

## Phase 12 — Coordinated action planning and approvals

### Build

- Convert requests such as “follow up with Parv and update Meera” into one persisted action plan
  containing independently versioned action proposals.
- Support one or more Teams reply actions with explicit destination, exact body, reason, evidence,
  ordering, and dependency metadata.
- Show a plan summary and separate approval card for every recipient or group.
- Allow edit, regenerate, approve, reject, and cancel per action plus safe bulk approval only when
  every exact payload is visible.
- Execute approved actions independently with one idempotency key and delivery state per action.
- Do not execute a dependent action if its prerequisite fails or is uncertain unless the manager
  explicitly revises the plan.
- Present combined progress and final results in the same Prism conversation.

### Completion criteria

- One manager request can prepare coordinated drafts for multiple employees or groups.
- Approving one card never approves another card implicitly.
- A recipient or content change invalidates only the affected approval.
- Partial failure is visible per action and never triggers blind replay of successful actions.
- Every outbound message still appears from the connected manager account.

### Testing

- Test mixed approve/reject/edit outcomes, ordering, dependency failure, double-clicks, retries,
  partial Graph failure, and ambiguous delivery.
- Test that model output cannot add a hidden recipient or execute an unrendered proposal.
- Test exact payload hashes and idempotency independently for every action.

## Phase 13 — One-chat frontend redesign and final v2.1 release gate

### Build

### Completion criteria

## Final v2.1 release criteria

Prism v2.1 is complete only when all of the following are true:

- The manager can complete the canonical journey entirely through the web UI.
- The manager interacts through one primary Prism conversation rather than one Prism chat per
  Teams source.
- Each job reads only its explicit or resolved-and-disclosed authorized source set.
- The analysis is evidence-backed and unsupported citations are rejected.
- Every exact approved message is sent as the connected manager.
- No automated path can bypass approval.
- Duplicate requests and ordinary retries do not intentionally duplicate messages.
- Job progress, evidence, approval, execution, delivery, and feedback survive an API restart.
- Fake-provider end-to-end tests pass without external network access.
- One controlled real-provider and real-Microsoft smoke test passes.
- Existing Prism tests and database migrations remain green.
- Existing selected-source history remains readable after the one-conversation migration.

## Recommended implementation order

Phases 0–8 establish the safe selected-source baseline. Continue sequentially through Phases 9–13
to turn that baseline into the actual v2.1 product: one manager conversation with optional source
constraints, multi-source understanding, and independently approved coordinated actions. Reuse the
existing evidence, proposal, approval, execution, preference, and audit boundaries; do not bypass
them in the redesign.
