# Prism v2.1 Phase 1: provider-independent intelligence

## Outcome

Prism model generation now crosses the `LLMProvider` contract. Azure OpenAI remains compatible,
standard OpenAI API keys are supported for local BYOK testing, and automated tests can use a
deterministic fake without network access.

For local development, Prism can invoke the installed Codex CLI and let that CLI use its own
`~/.codex/auth.json`. Prism checks that the file exists but never parses, copies, logs, or exposes
its contents. This adapter is rejected unless `APP_ENV=development`.

## Local configuration

Keep model calls disabled while validating configuration:

```dotenv
INTELLIGENCE_LLM_ENABLED=false
LLM_PROVIDER=openai
LLM_MODEL=<supported-model-name>
OPENAI_API_KEY=<server-side-api-key>
```

When an API key with API billing is available, set `INTELLIGENCE_LLM_ENABLED=true` and restart the
API. Azure remains available with `LLM_PROVIDER=azure_openai` and the existing Azure variables.

For the temporary local Codex path requested during development:

```dotenv
APP_ENV=development
INTELLIGENCE_LLM_ENABLED=true
LLM_PROVIDER=codex_local
LLM_MODEL=
CODEX_CLI_PATH=/absolute/path/to/codex
CODEX_AUTH_PATH=/Users/yashmandi/.codex/auth.json
```

Leaving `LLM_MODEL` blank uses the model selected by the Codex CLI configuration. The subprocess is
ephemeral, runs in a temporary directory with a read-only sandbox, and is instructed not to inspect
files or use tools.

Common request policy is configured with `LLM_TIMEOUT_SECONDS`, `LLM_TOTAL_TIMEOUT_SECONDS`, and
`LLM_MAX_ATTEMPTS`. `LLM_REASONING_MODEL` optionally selects the stronger model used by complex
or repaired decisions.

## Safe status contract

`GET /api/v1/provider/status` returns only:

- provider name;
- configured model name;
- `ready`, `disabled`, `not_configured`, or `invalid` state;
- a safe display message.

It never returns an API key, authorization header, endpoint credential, prompt, or message body.
The Settings screen renders this contract in its **AI provider** card.

## Web BYOK management

The Settings screen also lets the authenticated manager save, replace, or remove an OpenAI API
key. The key is submitted once to the API and encrypted with Fernet before PostgreSQL persistence.
The browser receives only a last-four mask and never stores the credential in local storage.

`PROVIDER_CREDENTIAL_ENCRYPTION_KEY` can provide a dedicated Fernet key. When it is blank, Prism
uses `MICROSOFT_TOKEN_ENCRYPTION_KEY`, allowing the existing local installation to reuse its token
encryption setup. A saved database credential takes precedence over the development `codex_local`
provider. Removing it returns Prism to the server-configured provider.

## Adapter contract

Every provider exposes structured generation, plain-text generation, configuration readiness, and
a default model. Results normalize output text, provider model, request ID, and usage. The existing
metering facade records provider, token usage, latency, status, and estimated cost independently of
the selected adapter.

Structured output uses JSON Schema generated from the Pydantic response model. The standard OpenAI
adapter uses Structured Outputs through Chat Completions, consistent with the
[official OpenAI Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat).

- [x] Provider contract supports structured and plain-text generation.
- [x] Azure OpenAI is behind the provider contract.
- [x] Standard OpenAI BYOK adapter exists.
- [x] Deterministic fake provider exists for automated tests.
- [x] Provider selection, model, timeouts, total timeout, and attempts are configurable.
- [x] Usage and errors retain a provider-neutral application boundary.
- [x] Safe provider-status API and visible Settings card exist.
- [x] OpenAI BYOK can be added, replaced, masked, and removed from Settings.
- [x] UI-managed API keys are encrypted in PostgreSQL and never returned to the browser.
- [x] Codex authentication stays owned by the local CLI and is restricted to development.
- [ ] A real OpenAI request is manually validated with a separately supplied API key.

The real-provider check is opt-in because it incurs external API usage and requires an API account;
it does not block deterministic development or CI.
