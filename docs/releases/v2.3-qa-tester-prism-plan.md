# v2.3 Plan: QA Tester Prism with a live "computer"

Status: implemented (Phases 1-5). See "Implementation notes" at the end for where the build differs from this plan.
Owner: Yash. Date: 2026-11-02.

## 1. Goal

A Prism you hire as a QA tester. You ask it in chat to test a website. While it works, you watch its screen in the right sidebar. When it finishes, it reports back in chat.

**The end user only ever uses Prism.** They never sign in to, visit or see the QA swarm (`/Users/yashmandi/Downloads/agentic swarm`, API on `:8080`). The swarm is a hidden backend engine. Prism creates its targets and tasks, starts and follows its runs, and handles its approvals. No swarm link, name, id or error text is shown in Prism's UI.

### User journey

1. **Sign in to Prism.** Nothing else to set up as a user.
2. **Hire the tester.** Create a Prism and pick the "QA tester" role. Onboarding asks about QA-specific things (house rules, severity, which environments are off limits) and finishes as usual.
3. **Ask in chat.** For example: "test oneclarity.ai, check pricing and the contact form validation".
4. **Approve the plan.** The Prism replies in its own voice with a plan card:
   - site and environment;
   - pages and checks;
   - turn and budget limits;
   - bug filing: off;
   - Start and Edit buttons.
5. **Watch it work.** After you press Start, the computer panel opens on the right. It shows the latest screenshot, the current URL and step, an activity ticker, cases passed and failed, cost, and a Cancel button.
6. **Approve bugs, if any.** If the swarm pauses on `file_bug`, the Prism asks you in chat with Approve and Reject buttons, and sends your answer to the swarm.
7. **Read the report.** When the run ends, the Prism posts:
   - a short human summary;
   - a table of test cases;
   - each bug with its severity, steps and screenshot.

### Decisions already made (from Q&A)

| Topic | Decision |
|---|---|

| Capability | A "QA tester" role chosen at onboarding (`template_key = "qa_tester"`) |
| Start | The Prism shows a plan; the run starts only after you approve it |
| Report | Human summary, test-case table, bugs with screenshots, bug-filing approvals in chat |

| Swarm visibility | Invisible to end users. No swarm UI, links or terms in Prism. |

## 2. Swarm API contract (verified from source)

Auth is a cookie session: `POST /api/v1/auth/login` with `{email, password}`. A request without a session returns 401 `{"error":{"code":"unauthorized"}}`. On a 401, the client logs in once and retries.

| Need | Endpoint | Notes |
|---|---|---|
| Health | `GET /api/v1/runtime/status` | `workers_online`, `azure_configured`, `deployment` |
| Agents | `GET /api/v1/agents` | Pick the agent named "QA Agent" (configurable) |
| Targets | `GET/POST /api/v1/targets` | `TargetCreate{name, base_url, environment, notes, extra_origins, test_login?, repo_url?}` |
| Task | `POST /api/v1/tasks` | `{title, goal, agent_id, target_app_id, scope{urls, features, acceptance_criteria, allow_bug_filing, focus}}` |
| Start | `POST /api/v1/tasks/{id}/runs` | `RunStart{mode:"single", pages?, max_turns(5-300)?, budget_usd(<=50)?}` |
| Run | `GET /api/v1/runs/{id}` | `status`, `summary`, `error`, `cost_usd`, `total_cost_usd`, tokens, `started_at`, `ended_at` |
| Events | `GET /api/v1/runs/{id}/events?after_seq=N` | `[{seq, type, payload, created_at}]` |
| Live | `GET /api/v1/runs/{id}/stream?after_seq=N` | SSE: `run_event` (id=seq), `run` (full run), `end`. Polls every 0.6 s |
| Screens | `GET /api/v1/runs/{id}/artifacts`, `GET /artifacts/{id}/file` | `kind=screenshot`, `mime`, `meta` |
| Results | `GET /runs/{id}/test-cases`, `GET /runs/{id}/bugs` | statuses `pass/fail/blocked/skipped/pending`; severity `critical/high/medium/low` |
| Approvals | `GET /api/v1/approvals`, `POST /approvals/{id}/decision` | `{decision: approve/reject, comment}` returns `resume_run_id` (a **new run** id) |
| Cancel | `POST /api/v1/runs/{id}/cancel` | |

Run statuses:

- active: `queued`, `running`, `waiting_approval`, `waiting_children`;
- terminal: `succeeded`, `failed`, `cancelled`, `timed_out`.

Event types and payloads:

- `tool_call {tool, arguments}`, where `arguments.url` / `element` / `text` say what the agent is doing;
- `tool_result {tool, output, ms}`;
- `message {text}`;
- `status {status}`;
- `log {text}`;
- `usage`;
- `artifact {kind:"screenshot", ...}`.

### Important limitation: screenshot frequency

The swarm only saves screenshots when the agent calls `browser_take_screenshot`. Its prompt asks for one per failure and at most one per passing page. So the screen image updates every few steps, not after every click.

To make the screen still feel live, the panel will:

- show the latest screenshot as the screen;
- overlay what the agent is doing right now, from `tool_call` events (for example "Navigating to /pricing", "Clicking 'Book a demo'", "Typing in Email"), updated every 0.6 s from SSE;
- show the current URL in a fake browser address bar, from the latest `browser_navigate` arguments.

**Later option (needs a swarm change, out of scope):** take an automatic screenshot after every navigate or click, or add a CDP screencast for real video. The panel is designed so either can replace the image source without UI changes.

## 3. Architecture

```
Browser (Prism UI)                Prism API (FastAPI)                  QA swarm (:8080)
  chat ──POST /qa/plan────────▶ QaPlanService (LLM parse) ─────────▶ (none)
  plan card ──POST /qa/runs──▶ QaRunService.start ──login/target/task/run──▶
  computer panel ◀─SSE /qa/runs/{id}/stream── QaRunService.relay ◀──SSE── /runs/{id}/stream
  screenshot <img> ◀─GET /qa/artifacts/{id}── proxy (cookie stays server-side) ◀── /artifacts/{id}/file
  report message ◀── QaRunWatcher (background) ── polls run until terminal, stores report
```

Key points:

- **The swarm session never reaches the browser.** Prism proxies the stream and screenshots, so the swarm cookie and password stay on the server.
- **Reports arrive even if you close the tab.** A background watcher in Prism's existing scheduler finishes runs and posts the report into the thread.
- **Approvals:** the watcher detects `waiting_approval`, stores a pending approval and posts a chat card. After your decision, Prism follows `resume_run_id`, and the same QA run record continues on the new swarm run.

## 4. Backend changes (Prism)

### 4.1 Data model (migration `0042_qa_runs`)

`qa_runs`:

- links: `id`, `prism_id` FK, `thread_id` FK, `request_message_id`;
- state: `state` (`planned`, `starting`, `running`, `waiting_approval`, `succeeded`, `failed`, `cancelled`, `timed_out`, `error`);
- the plan: `plan` JSON (site, pages, features, criteria, limits, allow_bug_filing);
- swarm ids: `swarm_target_id`, `swarm_task_id`, `swarm_run_id`, plus `swarm_run_ids` JSON (history across approval resumes);
- live state: `last_event_seq`, `current_url`, `current_activity`, `latest_screenshot_id`;
- results: `cases` JSON counts, `cost_usd`, `report` JSON;
- `started_at`, `ended_at`, timestamps.

`qa_approvals`: `id`, `qa_run_id`, `swarm_approval_id`, `action`, `payload`, `status`, `decided_at`, `comment`.

Other changes:

- Add `"qa_tester"` to the allowed values of `PrismCreate.template_key` (`app/schemas/prism_v22.py:36`).
- Update `tests/test_models.py`.

### 4.2 Services

`app/services/qa_swarm_client.py`: the httpx client for the swarm.

- Logs in with a cookie jar and re-logs in once on a 401.
- Timeouts: 10 s, and no read timeout for the stream.
- Typed helpers: `status()`, `agents()`, `find_or_create_target(base_url)`, `create_task(...)`, `start_run(...)`, `run(...)`, `events(after_seq)`, `stream(after_seq)` (async generator), `artifacts()`, `artifact_file()`, `test_cases()`, `bugs()`, `approvals()`, `decide()`, `cancel()`.
- Safe errors only. Raw exception text never leaks, following commit 4ab362d.

**Config:** `app/core/config.py` gains the `qa_swarm_`* settings. If they are missing, the QA tester role still appears, but its Prism says in chat: "My testing workspace isn't set up yet, ask your admin." `scripts/prism_admin.py qa-check` lets the operator verify the connection (log in + workers online).

`app/services/qa_plan_service.py`: turns a chat message into a plan.

- An LLM call with a structured output: `{base_url, pages[], features[], acceptance_criteria[], environment, notes, needs_clarification, question}`.
- Falls back to a regex URL extraction if the model fails.
- Applies safety defaults:
  - `allow_bug_filing=false`;
  - `max_turns=60`;
  - `budget_usd=1.0`;
  - production gets a note: "Read-only. Validation only. Never submit forms with valid data."
- Merges in the Prism's working agreement and preferences (house rules).
- If the message has no URL, `needs_clarification` makes the Prism ask "Which site should I test?" instead of returning a plan.

`app/services/qa_run_service.py`:

- `plan(db, prism, thread, text)`: creates a `qa_run` in state `planned` and a chat message with the plan card.
- `start(db, qa_run_id, edits?)`: target → task → run, then state `running`.
- `cancel(...)`.
- `sync(db, qa_run)`: one poll step that pulls new events after `last_event_seq` and updates the URL, activity, screenshot and counts. It detects:
  - `waiting_approval`: creates a `qa_approval` and an approval chat card;
  - a terminal status: builds the report.
- `decide(db, approval_id, decision)`: calls the swarm, then switches `swarm_run_id` to `resume_run_id`.
- `build_report(...)`: fetches cases, bugs and artifacts. It then writes a short summary with the LLM in the Prism's persona (falling back to a template), and stores `report` JSON plus one chat message.

**Watcher:** a scheduler job that runs every 3 s. It calls `sync` on every non-terminal `qa_run`, using a `FOR UPDATE SKIP LOCKED` lease so it never overlaps with itself or with the live stream.

### 4.3 Chat routing

Today, `ChatIntentService.respond` and then the Teams job flow (`agent-chat.js:1415`).

New: for a Prism with `template_key == "qa_tester"`, a test request goes to the QA flow first.

- Detection: a URL or domain, or test words (test, QA, check the site, smoke, regression, verify) → `POST /api/v2/prisms/{id}/qa/plan`.
- Everything else (small talk, Teams questions) keeps the existing flow.

### 4.4 API routes (`app/api/routes/qa.py`, behind the `PRISM_V23_ENABLED` flag + operator token)

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/v2/qa/status` | Whether testing is available (true/false + a friendly reason), with no swarm details |
| POST | `/api/v2/prisms/{id}/qa/plan` | Chat message → plan card |
| POST | `/api/v2/qa/runs/{id}/start` | Approve plan (optional edits) |
| POST | `/api/v2/qa/runs/{id}/cancel` | Cancel |
| GET | `/api/v2/prisms/{id}/qa/runs` | Run list for the computer panel |
| GET | `/api/v2/qa/runs/{id}` | Run state + report |
| GET | `/api/v2/qa/runs/{id}/stream` | SSE relay: `activity`, `screen`, `progress`, `approval`, `done` |
| GET | `/api/v2/qa/artifacts/{qa_run_id}/{artifact_id}` | Screenshot proxy (checks the artifact belongs to the run) |
| POST | `/api/v2/qa/approvals/{id}/decision` | Approve/reject bug filing |

Chat messages get a `kind` in `metadata` (`qa_plan`, `qa_approval`, `qa_report`) so the UI can render cards. This reuses `AgentThreadMessage` with no new message table.

### 5.1 No settings for the swarm

There is no user-facing swarm setting. The operator configures it once in `.env`.

  - severity guidance;
  - environments that need extra care;
  - whether bug filing is allowed.

  The answers feed into the working agreement, and from there into every plan.

### 5.3 Chat (`agent-chat.js`)

**Plan card.**

- Shows the site, environment badge, pages, checks, limits and bug filing state.
- Buttons:
  - **Start testing**;
  - **Edit**: inline edit of pages, checks and limits;
  - **Cancel**.

**Running card.** A compact live line ("Testing oneclarity.ai · 4/9 cases · $0.21") plus a "Watch" button that opens the computer panel.

**Approval card.** Bug title, severity, steps and screenshot, with Approve and Reject buttons.

**Report message.**

- The summary in the Prism's voice.
- Collapsible test-case table: status pill, title, Given/When/Then and notes.
- Bug list: severity pill, steps, expected vs actual, and a screenshot thumbnail that opens a lightbox.
- Footer: duration and pages covered. Cost is shown as Prism usage. There are no external links; screenshots are served by Prism's proxy.

### 5.4 Computer panel (right sidebar, like the reference screenshot)

- A monitor icon button in the chat header, shown only for QA tester Prisms, opens a "Computer" drawer panel.
- **Screen:**
  - a 16:10 frame with a fake browser chrome (traffic lights + address bar showing the current URL);
  - the latest screenshot cross-fades in;
  - when there is no screenshot yet, an idle desktop with the Prism logo.
- **Caption:** "{Prism name}'s screen". A live dot plus the status (Working / Waiting for you / Idle).
- **Now:** the current activity line, updated from SSE, e.g. "Clicking 'Contact sales'".
- **Progress:** cases pass/fail/blocked bar, turn x/max, cost vs budget, elapsed time; a Cancel button.
- **Activity ticker:** the last ~20 actions, collapsible.
- **Runs:** past runs (site, result, date). Clicking one shows its last screen and opens its report in chat.
- The panel auto-opens when a run starts. It keeps working if you switch Prisms, because the stream is tied to the run, not the open view.
- Reconnect: the `EventSource` resumes with `after_seq`; if SSE fails it falls back to polling `GET /qa/runs/{id}`.

### 5.5 Home / Prism directory

- A QA tester Prism shows "Testing oneclarity.ai…" as its live status while a run is active.
- The finished report counts as an update in the existing proactive updates feed.

## 6. Safety rules (enforced server-side, not just in the prompt)

- `allow_bug_filing` stays false unless:
  - the working agreement allows it, **and**
  - you toggle it on the plan card.
- Production targets always get the read-only note added to target notes and task focus.
- Hard caps: `max_turns <= 150`, `budget_usd <= 3`. Higher values are refused with a clear message.
- Only `http(s)` URLs. `localhost`/private IPs are allowed only if `QA_ALLOW_LOCAL_TARGETS=true` in `.env` (default on for dev).
- Never send the swarm password, cookie, ids, URL or raw errors to the browser or into LLM prompts. User-facing errors use the Prism's own voice ("I couldn't reach the site", "My testing workspace is offline").
- Every swarm call is logged to `activity_events` (start, cancel, decision).

## 9. Risks and open points

- **Screen freshness:** see section 2. The screen image only changes when the agent takes a screenshot. If this feels too static, the fix is in the swarm (auto-screenshot per action or CDP screencast), which is a separate change you approve.
- **Approval resume creates a new run id.** Prism must follow it; this is covered in `decide` and by a dedicated test.
- **Two workers are online.** Runs may be picked up by either; this has no impact on Prism.
- **Cost:** each run uses Azure gpt-5-mini on the swarm side, and Prism adds two small LLM calls (plan + summary).
- **Model:** plan and report calls use Prism's existing provider settings.

## 10. Implementation notes

Where the build differs from the plan above:

- **No `PRISM_V23_ENABLED` flag.** The QA routes sit behind `PRISM_V22_ENABLED` and the operator token like the rest of v2.2.
- **Live view is Prism's own stream.** `/api/v2/qa/runs/{id}/stream` reads Prism's database, which a background watcher keeps current by following the swarm every `QA_WATCHER_INTERVAL_SECONDS` (default 2 s). The browser never talks to the swarm, and closing the tab does not stop a run or lose its report.
- **Screenshots are addressed by number** (`/api/v2/qa/runs/{id}/screens/{n}`), never by the swarm's artifact ids.
- **Bug filing is never offered on production sites**, even if the Prism's agreement allows it; it can be turned on in the plan card for staging/local sites when the agreement includes "File bugs for my approval".
- **Swarm errors are never shown.** A failed run is reported in the Prism's own words; the raw error stays in logs only.
- **Operator settings:** `QA_SWARM_URL`, `QA_SWARM_EMAIL`, `QA_SWARM_PASSWORD`, `QA_SWARM_AGENT`, `QA_ALLOW_LOCAL_TARGETS`, `QA_MAX_TURNS_CAP`, `QA_BUDGET_CAP_USD`, `QA_WATCHER_ENABLED`, `QA_WATCHER_INTERVAL_SECONDS`. Check the connection with `python scripts/prism_admin.py qa-check`.
- **Swarm prerequisite:** the swarm worker starts the browser with `npx @playwright/mcp`, so the machine running the worker needs a working Node.js.

Code map: `app/models/qa.py`, `app/services/qa_swarm_client.py`, `qa_plan_service.py`, `qa_run_service.py`, `app/api/routes/qa.py`, `app/static/js/qa-tester.js`; tests in `tests/test_qa_tester_integration.py` (fake swarm) and `tests/e2e/test_qa_tester.py` (written, not yet run).
