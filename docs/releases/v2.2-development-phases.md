# Prism v2.2 development phases

## Objective

Prism v2.2 adds multiple private, specialized Prisms on top of the completed v2.1 manager-agent
foundation. Each Prism has an isolated identity, conversation, onboarding agreement, memory,
Microsoft Teams source policy, triggers, schedules, proactive observations, notifications, and
approval requests.

This plan is the authoritative implementation sequence for v2.2. Each phase must satisfy its
completion criteria and tests before the next phase becomes the main development focus.

## Release boundary

### Included

- Local, single-user operation.
- Unlimited Prisms subject to configurable operational budgets.
- Blank creation and one versioned Executive Assistant template.
- Dynamic conversational onboarding with selectable and custom answers.
- User-confirmed, versioned working agreements.
- One continuing web conversation and isolated memory per Prism.
- All accessible Teams chats as the default read scope, with optional restrictions.
- Manual, scheduled, event-driven, and continuous/polling triggers.
- Evidence-backed proactive updates and recommendations.
- Browser notifications only while a Prism page is open.
- Conservative cross-Prism event and notification deduplication.
- Approval-gated Teams drafts and delivery through the v2.1 execution path.
- Durable restart recovery, audit history, usage limits, and local observability.

### Excluded

- Multi-user, multi-tenant, sharing, and role-based access.
- A combined updates inbox.
- Closed-browser push notifications.
- Autonomous external actions.
- Teams channels, Outlook email/calendar, Jira, Slack, and ClickUp.
- A Prism bot installed in Teams.
- Cross-Prism memory sharing or delegation.
- Guaranteed monitoring while the local API is stopped.

## Release-wide invariants

These must be enforced by code and database constraints, not only by model prompts:

1. Every Prism-owned record resolves to exactly one `prism_id`.
2. A Prism cannot retrieve another Prism's conversation, preferences, memory, observations, or

   private configuration.
3. User-level Microsoft and model credentials are referenced, never copied into Prism prompts or

   records.
4. Teams content is untrusted evidence and cannot change a Prism's policy or approve an action.
5. All-chat scope means all chats accessible through the connected delegated account; it never

   expands Microsoft permissions.
6. An exclusion is applied before message content enters the evidence snapshot or model context.
7. Paused, unconfirmed, archived, or invalidly configured Prisms cannot start automatic runs.
8. One trigger occurrence has one stable idempotency key per Prism.
9. Monitoring may read and recommend, but no proactive run may directly perform a Graph write.
10. Every proposed Teams message uses the existing exact-recipient, exact-content approval flow.
11. Editing a working agreement invalidates incompatible pending automatic work and requires

    reconfirmation before monitoring resumes.
12. A browser notification is never the system of record; the update must already be durable.
13. Deduplication may suppress a duplicate alert but must not erase Prism-specific observations.
14. Automatic work has bounded source, message, token, duration, retry, and concurrency budgets.
15. A retry cannot intentionally duplicate a conversation update, approval proposal, Graph write,

    or browser alert.

## Frontend target

Keep the current server-rendered HTML, CSS, and browser-native JavaScript approach for v2.2. Do not
introduce a framework migration as part of this release.

### Primary areas

1. **Prism directory**
   - Cards or rows for each Prism.
   - Active, paused, onboarding, and archived states.
   - Unread, urgent, pending-approval, last-run, and next-run indicators.
   - Create, open, pause/resume, configure, and archive controls.
2. **Create Prism flow**
   - Executive Assistant or Blank choice.
   - Name and description.
   - Draft preservation and validation.
3. **Onboarding conversation**
   - One question at a time.
   - Single-select, multi-select, free-text, date/time, and schedule answers.
   - Back, skip-when-optional, custom answer, resume, and cancel.
4. **Working agreement review**
   - Human-readable mission, signals, scope, schedule, style, actions, and restrictions.
   - Edit answers, regenerate agreement, confirm, or remain in draft.
5. **Individual Prism workspace**
   - Existing v2.1 chat, evidence, progress, approval, and audit components scoped to a Prism.
   - Proactive update cards with urgency, confidence, evidence, recommendation, and limitations.
6. **Prism settings**
   - Name/description, source policy, triggers, schedules, tone, budgets, pause/archive.
   - Agreement revision history and reconfirmation state.
7. **Notification controls**
   - Browser permission status.
   - Enable/disable while open.
   - Clear explanation of local-only behavior.

### Required interface states

- No Prisms yet.
- Draft creation abandoned and resumed.
- Onboarding generation loading, invalid, unavailable, or partially answered.
- Working agreement awaiting confirmation or requiring reconfirmation.
- Active, paused, archived, permission-blocked, and provider-blocked Prism.
- Microsoft disconnected or missing consent.
- Monitoring idle, collecting, evaluating, rate-limited, degraded, or failed.
- No signal found.
- New informational update, urgent alert, duplicate suppressed, or update superseded.
- Browser notification unsupported, default, granted, or denied.
- Pending, stale, approved, rejected, delivered, failed, and ambiguous proposals.
- API restart and stale-tab recovery.

## Phase 0 — v2.2 boundary, baseline, flags, and contracts

### Build

- Record the v2.2 product boundary and invariants in an architectural decision record.
- Add a `PRISM_V22_ENABLED` feature flag, initially disabled.
- Preserve the complete v2.1 journey as a regression fixture.
- Inventory v2.1 models and APIs that will gain Prism ownership.
- Define versioned API contracts for Prism directory, creation, onboarding, agreement, settings,
runs, observations, and notifications.
- Define stable enums and state transitions before creating migrations.
- Create sanitized Teams fixtures for incidents, deadlines, blockers, unanswered questions,
customer discussions, ordinary chatter, and prompt-injection attempts.
- Define a deterministic clock and fake scheduler interface for automated tests.
- Define budgets for concurrent Prism runs, source count, messages, evidence characters, model
tokens, retries, and polling frequency.
- Document local-runtime truth: server-dependent monitoring and open-page notifications.

### Completion criteria

- v2.1 runs unchanged when v2.2 is disabled.
- Every new API response has a documented shape and safe error vocabulary.
- Every lifecycle transition and release invariant has a planned automated test.
- The migration approach identifies how the existing canonical v2.1 thread becomes the first
Executive Assistant Prism without data loss.
- Product copy does not imply 24/7 cloud monitoring or autonomous execution.

### Testing

- Record `make check`, PostgreSQL integration, migration, and browser-suite baselines.
- Validate clean-install and current-v2.1 database upgrade plans.
- Contract-test draft API schemas without writing production routes.
- Review all states at desktop and narrow widths using a static wireframe.
- Threat-model cross-Prism leakage, prompt injection, notification privacy, schedule replay,
duplicate sends, and unbounded polling.

## Phase 1 — Multi-Prism identity, lifecycle, and database isolation

### Build

- Add `prisms` with name, normalized name, description, lifecycle state, template metadata,
agreement revision, timestamps, and soft-archive fields.
- Add immutable lifecycle events for creation, activation, pause, resume, reconfirmation, and
archive.
- Add database ownership from Prism to its thread and all new v2.2 records.
- Add `prism_id` directly to hot-path v2.1 records where relying on a long relationship chain would
make authorization or queries unsafe.
- Add uniqueness and foreign-key constraints preventing cross-Prism thread/job/run attachment.
- Implement create, list, retrieve, rename, pause, resume, and archive services and APIs.
- Require agreement confirmation before activation.
- Use soft archive. Preserve historical proposals, executions, and audit events.
- Reject duplicate active names after normalized, case-insensitive comparison, or return a clear
choice to use a distinct name.

### Edge cases

- Empty, extremely long, whitespace-only, Unicode, emoji, and HTML-like names.
- Two tabs creating or renaming to the same name concurrently.
- Pause while a read-only run is active.
- Pause or archive while a proposal is waiting for approval.
- Resume after Microsoft credentials or provider configuration changed.
- Archive followed by a stale schedule tick.
- Attempt to fetch a thread or job using another Prism's route.

For v2.2, pausing stops new automatic runs but allows a safe read-only run already evaluating to
finish. It never auto-executes a proposal. Archiving cancels queued automatic runs and makes the
workspace read-only; historical pending proposals become non-executable and are marked cancelled.

### Completion criteria

- Multiple Prisms can exist with independent lifecycle states.
- Cross-Prism foreign keys and service authorization fail closed.
- Paused and archived Prisms cannot receive new automatic runs.
- Archive preserves a complete explanation of earlier Teams sends.
- Lifecycle operations are idempotent and safe under concurrent requests.

### Testing

- Migration-test clean, v2.1, and populated databases.
- Unit-test every allowed and forbidden lifecycle transition.
- Integration-test concurrent create, rename, pause, resume, and archive requests.
- Test Unicode normalization and hostile display strings.
- Test cross-Prism ID substitution on every new endpoint.
- Test stale scheduler and stale-browser commands after pause/archive.
- Test rollback preserves the original v2.1 records.

## Phase 2 — Prism directory, creation, and lifecycle UI

### Build

- Replace the single Agent entry point with a **Prisms** directory when v2.2 is enabled.
- Show name, short description, lifecycle state, last activity, next run, unread count, urgent
count, and pending approval count without creating a central feed.
- Add **Create Prism** with Executive Assistant and Blank choices.
- Validate name and description in both browser and API.
- Save creation as a durable draft before onboarding starts.
- Add pause/resume, configure, and archive controls with clear confirmations.
- Preserve deep links to a Prism conversation, observation, job, or proposal.
- Add empty, loading, partial-error, and stale-count states.
- Keep external text escaped and status readable without color.

### Completion criteria

- A user can create two draft Prisms, distinguish them, and resume either after refresh.
- Directory counts are derived from durable records and never from browser-only state.
- No directory element resembles a combined message inbox.
- Archived Prisms are hidden by default but available through an explicit filter.
- Keyboard and narrow-screen users can complete creation and lifecycle actions.

### Testing

- API tests for pagination, ordering, filtering, counts, and lifecycle commands.
- Browser tests for empty state, two-Prism creation, validation, refresh, deep links, pause/resume,
and archive confirmation.
- Test partial failure where counts cannot load but Prism navigation remains available.
- XSS-test names and descriptions.
- Accessibility-test focus return, labels, dialogs, live status, and keyboard order.

## Phase 3 — Dynamic onboarding engine

### Build

- Add onboarding sessions, questions, choices, answers, status, current position, and revision.
- Define a server-owned structured question schema supporting:
  - single choice;
  - multiple choice;
  - short or long text;
  - time and timezone;
  - schedule builder;
  - optional source restriction;
  - confirmation.
- Generate role-specific questions through the provider abstraction.
- Always inject required coverage for mission, urgent signals, regular output, scope, tone, allowed
proposals, and restrictions even if the model omits them.
- Validate generated options, lengths, types, and identifiers. Never execute model-supplied HTML,
URLs, code, or tool instructions.
- Allow custom answers alongside selectable options.
- Let later questions adapt to prior answers while keeping an audit of replaced questions.
- Support back, revise, resume, retry generation, skip optional, and cancel.
- Provide deterministic fallback questions when the provider is unavailable or invalid.
- Store only the user-approved answer, not hidden model reasoning.

### Edge cases

- Description is too vague, contradictory, malicious, or itself contains secrets.
- Model returns duplicate, irrelevant, excessive, or invalid questions/options.
- Provider times out halfway through onboarding.
- User changes the description after answering questions.
- Two tabs answer the same question differently.
- User selects an option and also supplies incompatible custom text.
- Timezone changes or a schedule falls in a daylight-saving gap/overlap.
- Source list is unavailable because Microsoft is disconnected.

Use optimistic concurrency through an onboarding revision. Conflicting answers return the latest
session and require the user to choose; they are never silently overwritten.

### Completion criteria

- Executive Assistant and arbitrary blank descriptions produce relevant but bounded onboarding.
- All required policy fields are collected or explicitly marked unresolved.
- Invalid model output falls back safely instead of blocking Prism creation.
- Refresh, provider retry, and API restart preserve progress.
- No question can directly alter database policy without a validated user answer.

### Testing

- Schema/contract tests across every question type.
- Golden tests for Executive Assistant, QA, Sales, daily brief, vague, and contradictory roles.
- Fuzz generated question identifiers, option values, Unicode, and maximum lengths.
- Test invalid JSON, missing required topics, duplicate choices, provider timeout, and fallback.
- Integration-test answer revision conflicts and resume after restart.
- Browser-test selectable choices, custom answers, back/edit, keyboard use, and error recovery.
- Prompt-injection-test descriptions asking the model to skip safety or reveal credentials.

## Phase 4 — Working agreements and Executive Assistant template

### Build

- Convert validated onboarding answers into a structured agreement plus plain-language preview.
- Store immutable agreement revisions with source answer IDs, template version, provider metadata,
and confirmation time.
- Require explicit confirmation to activate a Prism.
- Add edit flows that return the user to the relevant onboarding answer.
- Classify agreement changes:
  - display-only changes can apply immediately;
  - mission, scope, trigger, schedule, or action-policy changes pause automatic runs until confirmed.
- Add a versioned Executive Assistant template containing suggested defaults described in the
master plan.
- Keep all template values visible and editable. Copy a template version into a Prism so future
template releases do not mutate it.
- Render the active agreement and revision history in Prism settings.

### Completion criteria

- The user can understand how a Prism will behave before activating it.
- An active Prism always points to one confirmed agreement revision.
- Material edits cannot affect automatic work before reconfirmation.
- Existing Prisms do not silently change when the template version changes.
- Blank Prism and Executive Assistant both use the same runtime contract.

### Testing

- Golden-test agreement generation from representative onboarding answers.
- Test missing, conflicting, excessive, and unsafe agreement fields.
- Test confirm/edit/regenerate races and stale revision confirmation.
- Test template upgrade and old-Prism stability.
- Browser-test agreement review, source/schedule clarity, edit navigation, and confirmation.
- Snapshot-test display-safe agreement API payloads.

## Phase 5 — Per-Prism conversations, jobs, and memory isolation

### Build

- Give every confirmed Prism one canonical continuing conversation.
- Migrate the existing v2.1 canonical conversation into the first Executive Assistant Prism.
- Scope messages, jobs, sources, evidence, reviews, action plans, proposals, preferences, feedback,
and relevant memory retrieval to the active Prism.
- Require `prism_id` in runtime context rather than trusting a browser-supplied thread alone.
- Add the confirmed agreement and relevant Prism memory to model context with explicit provenance.
- Make “remember this” create a preference only for the active Prism.
- Add per-Prism unread markers and last-viewed cursor.
- Preserve existing v2.1 deep links by redirecting to the migrated Prism.
- Make job progress and recovery display inside the correct Prism conversation.

### Edge cases

- Same user asks two Prisms the same question.
- A copied job/proposal URL is opened under another Prism.
- Existing v2.1 preference has no obvious Prism owner.
- A stale tab sends a message after the Prism is paused or archived.
- An active agreement changes while a manual job is running.
- A memory lookup returns an item with missing or mismatched provenance.

### Completion criteria

- Two Prisms can discuss the same Teams evidence while maintaining different instructions and
memory.
- No query path returns another Prism's private conversation or preference.
- Existing v2.1 history, evidence, approvals, and delivery audit remain readable.
- A manual request still completes the v2.1 read/recommend/draft/approve/send journey.
- Unread counts are correct across refresh and multiple tabs.

### Testing

- Migration-test empty, typical, and large v2.1 histories.
- Add isolation tests for every repository/service query with two populated Prisms.
- Test explicit memory creation, retrieval, correction, and deletion per Prism.
- Test stale links, stale tabs, pause/archive, and agreement revision during jobs.
- Browser-test switching Prisms, separate history, unread state, and migrated deep links.
- Run the complete v2.1 end-to-end regression under the migrated Executive Assistant Prism.

## Phase 6 — Teams source policies and incremental event ingestion

### Build

- Add source policy mode `all_chats` as the default, plus explicit inclusions and exclusions.
- Store restrictions by stable Graph chat ID, with participant/topic labels as display metadata.
- Add safe handling for renamed chats, changed membership, deleted/inaccessible chats, and chats the
user newly gains access to.
- Normalize Teams activity into deduplicated `external_events` using tenant/user connection,
chat ID, message ID, edit/delete version, and timestamp.
- Add per-chat cursors and a global discovery cursor or bounded recent-activity scan.
- Implement incremental polling that works without a public callback.
- Reuse Graph webhooks when valid subscriptions are available, while passing all events through
the same normalization/idempotency path.
- Apply Prism exclusions before fetching message bodies when possible and always before model use.
- Handle pagination, edits, deletions, replies, empty messages, attachments metadata, throttling,
token refresh, and partial chat failure.
- Sort chat discovery by latest activity and bound every scan.

### Edge cases

- More chats than one poll cycle can process.
- A message is edited after it produced a signal.
- A message is deleted before evidence is reviewed.
- Two webhook events and polling discover the same message.
- Graph returns messages out of order or repeats a page.
- Chat becomes excluded while a run is queued.
- Chat membership changes after evidence collection.
- One inaccessible chat fails while all others are readable.
- 401, 403, 404, 429, timeout, and service failure.

### Completion criteria

- All accessible chats are eligible by default without requiring manual selection.
- Restrictions are reliably enforced and visibly disclosed.
- Polling works locally without ngrok.
- Webhook and polling overlap does not duplicate external events.
- A Graph failure produces a visible degraded state and bounded retry, not data loss or a busy
loop.
- Incremental scanning resumes from durable cursors after restart.

### Testing

- Mock Graph pagination, recency ordering, edits, deletes, duplicate pages, and malformed payloads.
- Test all-chats, include-only, exclusions, renamed chats, membership changes, and scope edits.
- Test cursor crash recovery before and after event commit.
- Test webhook/polling races and stable event idempotency.
- Test Graph error classes, retry-after behavior, token refresh, and partial failure.
- Load-test bounded scans across a large synthetic chat catalog.
- Perform one controlled live incremental read against consented chats.

## Phase 7 — Durable schedules, triggers, and local run coordination

### Build

- Add trigger policies for manual, scheduled, event-driven, and continuous monitoring modes.
- Add timezone-aware schedules with next-run calculation and an explicit missed-run policy.
- Add durable `prism_runs` with trigger type, occurrence key, agreement revision, source policy
revision, state, budgets, timestamps, and linked agent job.
- Use database claiming/leases so two workers or reload processes do not run the same occurrence.
- Add a coordinator that limits global and per-Prism concurrency.
- Coalesce rapid Teams events into a short evaluation window rather than starting one model call
per message.
- Skip inactive Prisms and record a safe reason.
- On startup, recover expired leases and decide whether a missed schedule should run once, skip, or
wait for the next occurrence according to policy.
- Expose run status and next scheduled run in the UI.

### Edge cases

- API reload creates two scheduler processes.
- Computer sleeps across several schedule times.
- Timezone or daylight-saving transition changes next run.
- User edits or disables a schedule while its run is queued.
- Many Prisms become due simultaneously.
- Continuous monitoring receives a burst of hundreds of messages.
- Provider or Graph is unavailable for longer than the retry window.
- Manual and scheduled runs overlap on the same Prism.

### Completion criteria

- One schedule occurrence creates at most one run.
- Automatic runs never start for paused, archived, unconfirmed, or invalid Prisms.
- Restarts recover safely without replay storms.
- Event bursts are coalesced and budgets are enforced.
- The UI honestly shows next run, last run, and degraded/skipped states.

### Testing

- Use a fake clock for recurrence, timezone, DST gap/overlap, sleep, and catch-up tests.
- Concurrency-test leases with two simulated workers.
- Test schedule edit/delete races, restart recovery, and stale occurrence keys.
- Load-test event coalescing and global/per-Prism concurrency limits.
- Test manual/scheduled overlap and cancellation semantics.
- Browser-test schedule creation, next-run display, pause/resume, and failure messages.

## Phase 8 — Proactive signal detection and recommendations

### Build

- Add a two-stage evaluation path:
  1. deterministic filtering and cheap candidate extraction;
  2. structured model evaluation only for relevant candidates.
- Evaluate candidates against the active confirmed agreement, not a global prompt.
- Support initial signal classes: production incident, deadline risk, blocker, unanswered important
message, and customer discussion.
- Produce structured observations containing summary, verified facts, inference, urgency,
confidence, evidence IDs, why it matters, suggested next step, unknowns, and fingerprint inputs.
- Reject unsupported citations and any destination not authorized by the v2.1 source/destination
resolver.
- Distinguish `no_signal` from provider failure or insufficient evidence.
- Add configurable unanswered-message windows so a new message is not immediately called
unanswered.
- Allow a scheduled run to produce a digest from recent observations and new evidence without
repeating every alert verbatim.
- Ensure information-seeking prompts do not automatically create a message draft. A proposal is
created only from explicit draft/send intent or a clearly configured proactive recommendation
path.

### Edge cases

- Jokes, hypotheticals, quoted old incidents, and “this is not a production issue.”
- Conflicting updates in different chats.
- Forwarded or copied messages attributed to the wrong person.
- A deadline mentioned without year/timezone.
- “Blocked” used in an unrelated context.
- Customer name ambiguous with an employee or project.
- A reply arrives while unanswered-message evaluation is running.
- Model returns high urgency without supporting evidence.
- Evidence exceeds context limits or one source fails.

### Completion criteria

- Fixed evaluation sets meet agreed precision thresholds for urgent alerts and useful-update
thresholds for non-urgent observations.
- Every material claim maps to stored evidence and the correct chat/person.
- Unsupported urgency is downgraded or rejected.
- Normal chatter produces no proactive update.
- Scheduled briefs identify material changes and unresolved items without pretending uncertainty is
fact.

### Testing

- Golden-test positive, negative, ambiguous, resolved, and evolving examples for every signal type.
- Test contradictions, negation, quotations, forwarded messages, mixed languages, and prompt
injection.
- Test unanswered-window boundaries with a fake clock and late replies.
- Test citation substitution, evidence truncation, partial source failure, and invalid model JSON.
- Measure precision/recall on a versioned sanitized evaluation dataset and record human judgments.
- Test that no informational request or observation directly performs an action.

## Phase 9 — Proactive workspace updates and browser notifications

### Build

- Render proactive observations as first-class messages in the correct Prism conversation.
- Show urgency, confidence, evidence, why it matters, recommendation, unknowns, created time, and
incident/update relationship.
- Add unread state and deep links from directory cards.
- Add a browser presence heartbeat for open Prism pages.
- Request Web Notification permission only after a clear user action.
- Create a notification only after the observation is durably stored.
- Keep notification content minimal and deep-link to the exact Prism observation.
- If permission is denied, unsupported, page closed, or delivery throws, retain an unread in-app
update and record the safe delivery result.
- Add per-Prism notification enablement and urgency threshold.
- Avoid repeated permission prompts.

### Edge cases

- Permission changes outside Prism.
- Multiple Prism tabs are open.
- Notification click opens an existing tab or a new one.
- Observation becomes resolved before notification delivery.
- User has archived or paused the Prism in another tab.
- Notification API accepts the request but the OS suppresses display.
- Sensitive Teams excerpts would exceed safe notification content.

### Completion criteria

- New updates always appear in the correct Prism conversation.
- At most one browser notification is attempted per notification record.
- Multiple tabs do not intentionally create multiple OS notifications.
- Denied or unavailable notification permission never blocks monitoring.
- Closing the page stops browser notification attempts without losing updates.

### Testing

- API tests for unread counts, presence expiry, delivery claims, and deep links.
- Browser tests for default/granted/denied/unsupported notification states.
- Multi-tab tests for one delivery claim and consistent unread state.
- Test notification sanitization, length, and absence of secrets/raw evidence.
- Test page close/reopen and API restart recovery.
- Accessibility-test in-app urgent updates independently of browser notifications.

## Phase 10 — Cross-Prism deduplication and incident evolution

### Build

- Create conservative signal fingerprints from exact external event IDs, evidence overlap, signal
class, involved entities, and bounded time window.
- Add incident clusters linking multiple Prism observations without merging their private memory or
instructions.
- Prefer deterministic evidence overlap; use model/semantic similarity only as a secondary hint.
- Suppress duplicate browser alerts while preserving each Prism's materially distinct explanation.
- Model incident evolution: opened, updated, resolved, reopened, and superseded.
- Link scheduled-digest mentions to the existing incident rather than creating new alerts.
- Provide an audit explanation for why an alert was grouped or not grouped.
- Allow a false grouping to be split without deleting observations.

### Edge cases

- Two unrelated incidents use the same words.
- One incident affects two projects and produces different role-specific consequences.
- A copied message appears in several chats.
- Incident resolves and later recurs.
- Evidence is edited or deleted after clustering.
- Two workers cluster the same observations concurrently.

### Completion criteria

- The same Teams event does not create repeated browser alerts across Prisms.
- Distinct incidents are not merged solely by text similarity.
- Each Prism retains its own observation and recommendation.
- Resolution and reopening are represented as updates, not silent mutation.
- Cluster operations are deterministic, idempotent, and auditable.

### Testing

- Golden-test exact duplicate, forwarded duplicate, similar-but-distinct, multi-role, resolution,
and reopening scenarios.
- Concurrency-test cluster creation and notification suppression.
- Test edited/deleted evidence and split correction.
- Measure false-group and missed-group rates on the evaluation dataset.
- Browser-test links between an observation and earlier incident updates.

## Phase 11 — Approval integration for proactive drafts

### Build

- Allow an observation or recommendation to create a v2.1 action plan and one or more Teams
proposals.
- Require explicit user drafting intent or agreement-authorized proactive proposal creation.
- Treat proposal creation as safe preparation, never approval.
- Resolve each destination independently from the read sources and show it explicitly.
- Inherit Prism, agreement revision, observation, evidence, and incident provenance.
- Reuse exact payload hashing, revisioning, expiration, idempotency, approval, and execution.
- Invalidate a pending proposal if the Prism is archived, destination access is lost, evidence
materially changes, or agreement changes incompatibly.
- Keep informational updates useful even when no proposal is present.

### Completion criteria

- A proactive incident can prepare an editable approval card in the correct Prism.
- No route, schedule, event, model output, or notification can approve or execute it.
- The exact approved Teams message is sent from the connected user's account once.
- Read scope and write destination remain visibly separate.
- Old v2.1 manual drafting continues to work.

### Testing

- Test explicit drafting, configured proactive suggestion, and no-draft informational paths.
- Test destination substitution, hidden recipients, stale evidence, agreement change, pause/archive,
expired approvals, and Microsoft reconnect.
- Re-run all v2.1 approval tampering, double-click, retry, ambiguous-send, and reconciliation tests.
- Test multiple proposals from one observation with independent decisions.
- Perform one controlled live proactive-draft approval to a self-directed test chat.

## Phase 12 — Feedback, tuning, budgets, and observability

### Build

- Record helpful/not-helpful, wrong urgency, wrong evidence, duplicate, and no-longer-relevant
feedback per observation.
- Let the user correct a Prism's signal preferences without editing the database.
- Keep learned preferences Prism-scoped and show how they affected later output.
- Require repeated evidence or explicit confirmation before turning behavior into a durable rule.
- Add configurable per-Prism operational budgets and safe global defaults.
- Record run latency, Graph reads, candidates, model calls, tokens, observations, false-positive
feedback, deduplication, notifications, proposals, and failures.
- Add health/status views for provider, Microsoft connection, scheduler, monitoring cursor, and
latest successful run without exposing secrets.
- Add retention/compaction policies for raw events and evidence while preserving action audit.

### Edge cases

- User feedback conflicts across observations.
- A learned preference would hide a mandatory safety alert.
- One Prism consumes the full model budget.
- A failing Prism retries continuously.
- Old raw Teams events expire while an approved action audit must remain explainable.

### Completion criteria

- Feedback changes only the intended Prism.
- Safety-critical configured signals cannot be silently disabled by inferred preference.
- Runaway polling, retries, or model usage is bounded and visible.
- The user can diagnose why a Prism is quiet, delayed, or failing.
- Retention removes eligible raw data without breaking proposal/delivery audit integrity.

### Testing

- Test preference precedence, correction, scope, expiry, and conflicting feedback.

## Final v2.2 release criteria

Prism v2.2 is complete only when all of the following are true:

- The user can create and operate at least two Prisms with different jobs.
- Dynamic onboarding produces a confirmed and inspectable working agreement.
- Each Prism has an isolated conversation, memory, settings, runs, and observations.
- Teams all-chat monitoring works with optional restrictions and without requiring ngrok.
- Manual, scheduled, event-driven, and continuous triggers create durable, bounded runs.
- Proactive updates are evidence-backed and useful on the agreed evaluation set.
- Browser notifications work while an authorized Prism page is open and degrade safely otherwise.
- Duplicate events do not cause repeated alerts, while role-specific observations remain intact.
- Every proposed Teams action stays approval-gated and exact-send/idempotency rules remain intact.
- Pause, archive, restart, provider failure, Graph failure, and stale-tab cases fail safely.
- The v2.1 history and canonical manual journey survive migration.
- Automated suites are network-isolated by default and pass with fake providers.
- A controlled real-provider and real-Microsoft smoke test passes.

## Recommended implementation order

Build sequentially. Phases 0–5 establish identity, onboarding, agreements, and isolation. Phases
6–10 add safe proactive monitoring and delivery. Phase 11 connects proactive work to the proven
approval engine. Phases 12–13 make the product tunable, observable, secure, and releasable.

Do not begin continuous monitoring before ownership, agreement confirmation, source restrictions,
durable run idempotency, and per-Prism isolation are enforced. Those are the foundations that make
proactive behavior safe.
